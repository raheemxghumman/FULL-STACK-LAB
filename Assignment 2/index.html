Section 3 · request workflow

Six statuses, six legal moves

Each status change has its own action endpoint. Any move not shown here is refused with 409, and CLOSED and CANCELLED are final. Click an arrow to see who can make that move, the endpoint, and its error codes, or press play to watch a request go all the way through.

Tip: click any arrow
5active requests per requester: any status except CLOSED or CANCELLED. The limit also applies to reopening.
3ASSIGNED or IN_PROGRESS jobs per technician. A fourth assignment gets 409.
1feedback per request, only once it is CLOSED. It is credited to the technician who did the final repair.
Section 1 · access control

A role is required, but ownership is checked too

RolesGuard checks the caller's role. RequestAccessPolicy then checks, inside the service, whether the caller owns or is assigned to that record. Someone else's existing record always gets 403, before any of its state is revealed.

REQUESTER

The only role public registration can create

  • Create requests: POST /requests
  • See their own requests and history
  • Edit or cancel, only while OPEN
  • Close or reopen their own RESOLVED work
  • One feedback per CLOSED request
  • Assign, start, resolve, or create categories

TECHNICIAN

Created only by the seed command

  • See the requests assigned to them
  • Start their assigned work
  • Resolve it with a 20-1000 character note
  • See the history of those requests
  • Assign work or close requests
  • Act on a job assigned to someone else

DISPATCHER

Created only by the seed command

  • See every request
  • Create, update and deactivate categories
  • Assign eligible technicians that have capacity
  • View system dashboards and technician ratings
  • Create requests, or start or resolve work (no impersonation)
Section 6 · request lifecycle

What one request passes through

These are the real stage logs of the instrumented route PATCH /api/requests/:id, recorded with LIFECYCLE_TRACE=true. Choose an outcome to see which stages run and which are skipped.

Guards run before pipesThat is why ownership is checked in the service and not in a guard: a guard has neither the validated DTO nor the stored record.
The interceptor never wraps errorsIt only maps successful responses. catchError re-throws the original exception, so Nest's standard error body and status code are kept.
The final log line always appearsThe middleware logs on the response's finish event. That covers 401s, 404s and pipe errors that never reach the interceptor.
Section 5 · NestJS architecture

Modules, constructor injection and a custom token

Controllers only handle HTTP, and every rule lives in a service. Storage sits behind the FIXFLOW_STORE token with a typed contract, so the store can be swapped without editing any service. Try it below.

StorageModule

Binds FIXFLOW_STORE to InMemoryFixflowStore; SeedService loads the seed on start. Exports the token.

AuthModule

Register and login, a JWT signed with the secret from .env, global JwtAuthGuard and RolesGuard.

UsersModule

UsersService: public views of users (never the hash), technicians. Exported.

CategoriesModule

Create, update and deactivate categories; names are unique regardless of case. CategoriesService is exported.

RequestsModule

Every workflow rule, RequestAccessPolicy for ownership, and the status transition table.

ReportsModule

Role-specific dashboards and technician ratings, always computed from stored data.
